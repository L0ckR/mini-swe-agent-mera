# mini-swe-agent fork for SWE MERA Stage II

> Историческая конфигурация. Текущий кандидат использует готовый Pi RL-адаптер
> и настоящий Pi SDK; см. [адаптацию готовой модели](pi-ready-model.md).
> Предыдущие источники сохранены в `experiments/mini_before_pi/submission_stage2`.

Основной harness — реальный форк **mini-swe-agent 2.4.6**, upstream commit
`04d809ceab9df28f9adaed044884180159172930`:
[GitHub fork](https://github.com/L0ckR/mini-swe-agent-mera),
[upstream](https://github.com/SWE-agent/mini-swe-agent/tree/04d809ceab9df28f9adaed044884180159172930).

В проекте и GitHub-форке загружаемые файлы лежат в `submission_stage2/`.
ZIP содержит содержимое каталога
без внешней папки. Фиксированный импорт организаторов:
`custom_agent.react_bash_agent:ReactBashAgent`.

## Почему выбран этот harness

mini-swe-agent предназначен для исправления задач в репозиториях, имеет компактный
цикл действий, заменяемые порты модели и окружения, обработку ошибок формата и
сохранение траекторий. Его README публикует результаты SWE-bench с конкретными
моделями; эти результаты не являются score нашего сабмита.

Для ядра нужны Jinja2 и Pydantic, уже установленные у организаторов. Текущий
OpenHands SDK требует более новые версии Pydantic и LiteLLM, чем закреплены в
окружении Harbor соревнования. У полного SWE-agent больше зависимостей и другая
интеграция жизненного цикла контейнеров. Это причины выбора переносимого ядра
mini для данного окружения, а не утверждение универсального превосходства.

## Что осталось от upstream

Управляющий цикл действительно выполняет vendored `DefaultAgent.run()` →
`step()` → `query()` → `execute_actions()`. Сохранены его конфигурация, обработка
FormatError/InterruptAgentFlow, лимиты шагов/стоимости/времени и формат траектории.
Эти возможности существовали в upstream и не считаются нашим нововведением.

Исходники до изменений и SHA256 сохранены в `vendor/mini_swe_agent/`. В сабмит
включены MIT LICENSE и `UPSTREAM.json`. Адаптация ядра ограничена async-вызовами
модели и Harbor, относительными импортами, монотонными часами и атомарной записью.
Глобальная загрузка пользовательского `.env` из upstream initializer удалена:
endpoint и ключ берутся только через model connection Harbor.

## Доработки под ограничения соревнования

| Изменение | Реализация и ожидаемая польза | Цена или ограничение |
|---|---|---|
| Полная постановка и deliverable | Сохраняется весь исходный instruction, включая раздел Submission за пределами issue. Если запрошен `change.diff`, он атомарно строится из всех implementation-изменений, включая новые файлы; отдельный временный Git index сохраняет настоящий index | 22 из 49 публичных постановок требуют такой файл. Это контракт задачи, не правило для всех задач; путь проверяется внутри `/testbed` |
| Literal search | Отдельный `search` ищет буквальный текст, включая `-h`/`--help`, возвращает строки с номерами и ограниченный контекст | Ограничены число файлов, размер и вывод. При усечении поиск нужно сузить; язык запросов отсутствует |
| Точное редактирование | `read_file`, `edit_file`, `create_file` исполняются в task-контейнере. Замена требует одного точного совпадения; неоднозначная правка ничего не меняет | Это строгий UTF-8 editor; нестандартные файлы можно обрабатывать через bash |
| Контекст длинной задачи | Model view сохраняет полные недавние ходы по доступному бюджету; до порога 42k оценённых токенов история не сжимается. Затем checkpoint сохраняет наблюдённые выводы, правки и проверки; дубли reasoning aliases не считаются дважды | Полная native trajectory сохраняется отдельно. Оценка токенов приближённая, сводка требует запроса и может потерять детали |
| Время на завершение | Общий бюджет 1680 секунд; 90 секунд отделены для review. В review отдельный запрос ограничен 45 секундами, последние 10 секунд оставляются для снимка состояния | Сложное решение может потребовать больше рассуждений; значения являются начальными настройками |
| Ограниченные повторы API | Временные ошибки повторяются в рамках общего дедлайна запроса и фазы; ошибки авторизации не повторяются | Слишком маленький request timeout может вредить медленной генерации |
| Проверки текущего patch | `run_tests` и распознанные тестовые bash-команды связываются с fingerprint содержимого и mode файлов. При изменении patch старый успех отмечается как устаревший; нулевое число тестов выделяется отдельно | Exit 0 сам по себе не доказывает корректность. Тихий assert-reproducer может быть полезен, поэтому отсутствие test summary не объявляется автоматическим провалом |
| Завершение | `finish` вызывается отдельно; harness возвращает actual diff, status, stat и `git diff --check HEAD`, затем предлагает сверить patch со всеми требованиями. Контракт запрещённых test-изменений проверяется и при отсутствии `change.diff` | Новые, изменённые и mode-изменённые тесты отклоняются, а не молча исключаются. Снимок diff и успех обычных тестов не заменяют проверку поведения |
| Сохранение репозитория | Startup показывает уже существующий checkout и доступные средства. Guard отклоняет распознанные команды стирания корня, `git reset`/`clean` и повторного clone поверх `/testbed` | Это защита от конкретных ошибочных действий модели, не полная sandbox. Границы выполнения задаёт task-контейнер, а в локальных диагностиках — bubblewrap |
| Выход из неуспешных циклов | Наблюдения о повторных exact edits с отсутствующим/неоднозначным текстом и grep usage вызывают короткую подсказку пересмотреть target и гипотезу | Механизм не выполняет действий, не подменяет return codes и не утверждает, что файл не изменился после shell-команд |
| Новые файлы | `create_file` включает в diff только созданный файл через `git add -N -- path` | Игнорируемый или недоступный файл сопровождается предупреждением |
| Конкурентная оценка | Один агент последовательно меняет один репозиторий; внутри задачи нет автоматического fan-out из нескольких моделей | Это сберегает пропускную способность при 20 одновременных задачах, выигрыш измеряется отдельно |

Экспериментальный `semantic_review=True` добавляет один запрос той же модели
без инструментов по исходному issue, фактическому diff и наблюдённым проверкам.
Он ограничен 40 секундами и 2048 output-токенами, пропускается при остатке
меньше 60 секунд и возвращает совет основному агенту. Это не verifier и не
автоматическое принятие решения. **По умолчанию semantic review выключен**:
локальная серия с ним дала как ложную критику правильной правки, так и пропуск
неполного решения. Доказательств прироста качества этой опции нет.

Модель остаётся `Qwen/Qwen3.8-27B-FP8` с фиксированной ревизией, 3 независимыми
репликами и контекстом 65536. Увеличения аппаратного бюджета относительно runner
нет. Сервер должен пройти неизменённую короткую проверку bash/pwd организаторов.

## Проверки и измерение результата

Проверки кода используют настоящие временные файлы и Git-репозитории,
реальные команды тестов и подставные ответы модели. Они проверяют код адаптера,
редактирование, поиск, экспорт diff, протокол, таймауты и сохранение логов.
Рендерится фактический шаблон зафиксированного checkpoint Qwen. Эти проверки
отделены от запусков живой модели.

Живые локальные диагностики используют небольшую `qwen3:8b-q4_K_M` под Ollama.
Первые две серии по три synthetic задачи дали before/after 0/3 против 0/3
и 1/3 против 1/3; одна публичная Click py-009 попытка задачу не решила.
Это не официальный Harbor-прогон и не pass@1 SWE MERA. Смена prompt wrapper,
snapshot кода или backend settings образует новое условие эксперимента;
результаты таких серий не доказывают эффект одной доработки.
[Подробные наблюдения](local-quality-results.md),
[анализ всех 49 публичных постановок](public-task-analysis.md).

Для честного сравнения подготовлен `profile=ported`: тот же fork, транспорт,
инструменты, промпт, task contracts и sampling, но без checkpoint-компактации,
резерва review и обязательного finish gate. Это контроль выбранных доработок,
не неизменённый upstream default. Стандартный профиль официального сабмита —
`mera`; semantic review в обоих профилях по умолчанию выключен.

На GPU-сервере нужно сравнить официальную baseline-конфигурацию, ported и mera
на одном полном публичном наборе, с одной попыткой на задачу, одинаковыми
ресурсами и concurrency. Для отделения эффекта модели дополнительно использовать
одинаковую модель в сравнении harness. Считать solved/total, ошибки, таймауты,
длительность и расход токенов. Не выбирать победителя только по числу пройденных
локальных unit-тестов.

Траектории сохраняются в `mini-swe-agent.json`, запросы и checkpoints — в
`model-audit.json`, действия и финальные проверки — в `tool-audit.json`,
fingerprints patch и результаты команд — в `evidence.json`.
Это native audit logs, не обещание ATIF-совместимого экспорта.

Publisher формирует проверяемый inventory исходников и fixtures: `scripts/`,
pinned зависимости в `mera_requirements.txt`, provenance в `vendor/`, проверки
в `tests_mera/`, inventory публичных постановок с URL/SHA256 и компактные
диагностические сводки в `experiments/results/`. Полные внешние statements,
raw jobs, model cache и рабочие checkouts
в список не входят. `MERA_SOURCE_MANIFEST.json` фиксирует хеш каждого
публикуемого файла; команда `inventory` не обращается в сеть. Обновление
GitHub-ветки выполняется отдельной явной командой `publish`.

Для отдельного checkout форка после публикации соответствующего source snapshot:

```bash
uv venv --python 3.12 .venv
uv pip install --python .venv/bin/python -r mera_requirements.txt
.venv/bin/python scripts/fetch_public_statements.py
.venv/bin/python -m unittest discover -s tests_mera -v
.venv/bin/python scripts/package_submission.py submission_stage2 --output dist/mera-mini-stage2.zip
```

Локальный runner требует Linux и работающий bubblewrap. Он прекращает запуск,
если изоляция недоступна; команды модели работают внутри `/testbed` без сети.
Маленькая модель вызывается через отдельно запущенный inference endpoint;
`ollama_bridge.py` сохраняет реальную модель и ограничения локального backend.
Диагностические snapshots и подробные native logs остаются локально, в отчёты
попадают выбранные параметры, хеши и фактические acceptance-результаты.

Сборка целевого inference-образа, его startup/throughput на заявленных GPU и
SWE MERA pass@1 пока не измерены. Локальная RTX 4070 Ti SUPER 16 ГБ не вмещает
эту production-конфигурацию модели.

## Следующие эксперименты

1. Подобрать thinking budget и timeout по фактической задержке при concurrency 20.
2. Сравнить exact editor с bash-only при одинаковых модели и бюджете времени.
3. Сравнить checkpoint с полным контекстом и подобрать порог сжатия.
4. Измерить эффекты literal search, наблюдаемой свежести проверок и подсказок
   выхода из циклов на неизменных задачах и backend. Semantic review оценивать
   отдельно с учётом уже наблюдавшихся ложных выводов проверяющей модели.

Скрытые оценочные тесты, gold patches, подмена verifiers и готовые решения
задач не используются. Оценка и сетевые ограничения определяются организаторами.
