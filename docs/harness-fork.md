# mini-swe-agent fork for SWE MERA Stage II

Основной harness — реальный форк **mini-swe-agent 2.4.6**, upstream commit
`04d809ceab9df28f9adaed044884180159172930`:
[GitHub fork](https://github.com/L0ckR/mini-swe-agent-mera),
[upstream](https://github.com/SWE-agent/mini-swe-agent/tree/04d809ceab9df28f9adaed044884180159172930).

В проекте и GitHub-форке загружаемые файлы лежат в `submission_stage2/`.
ZIP содержит содержимое каталога
без внешней папки. Фиксированный импорт организаторов:
`custom_agent.react_bash_agent:ReactBashAgent`.

## Почему выбран этот harness

mini-swe-agent предназначен для исправления задач в репозиториях, имеет компактный
цикл действий, заменяемые порты модели и окружения, обработку ошибок формата и
сохранение траекторий. Его README публикует результаты SWE-bench с конкретными
моделями; эти результаты не являются score нашего сабмита.

Для ядра нужны Jinja2 и Pydantic, уже установленные у организаторов. Текущий
OpenHands SDK требует более новые версии Pydantic и LiteLLM, чем закреплены в
окружении Harbor соревнования. У полного SWE-agent больше зависимостей и другая
интеграция жизненного цикла контейнеров. Это причины выбора переносимого ядра
mini для данного окружения, а не утверждение универсального превосходства.

## Что осталось от upstream

Управляющий цикл действительно выполняет vendored `DefaultAgent.run()` →
`step()` → `query()` → `execute_actions()`. Сохранены его конфигурация, обработка
FormatError/InterruptAgentFlow, лимиты шагов/стоимости/времени и формат траектории.
Эти возможности существовали в upstream и не считаются нашим нововведением.

Исходники до изменений и SHA256 сохранены в `vendor/mini_swe_agent/`. В сабмит
включены MIT LICENSE и `UPSTREAM.json`. Адаптация ядра ограничена async-вызовами
модели и Harbor, относительными импортами, монотонными часами и атомарной записью.
Глобальная загрузка пользовательского `.env` из upstream initializer удалена:
endpoint и ключ берутся только через model connection Harbor.

## Доработки под ограничения соревнования

| Изменение | Реализация и ожидаемая польза | Цена или ограничение |
|---|---|---|
| Точное редактирование | `read_file`, `edit_file`, `create_file` исполняются в task-контейнере. Замена требует одного точного совпадения; неоднозначная правка ничего не меняет | Это строгий UTF-8 editor; нестандартные файлы можно обрабатывать через bash |
| Контекст длинной задачи | До бюджета около 42k токенов сохраняется история; затем checkpoint хранит подтверждённые выводы, правки и проверки плюс недавние полные ходы | Сводка требует вызова модели и может потерять детали; это нужно оценивать на реальных задачах |
| Время на завершение | Общий бюджет 1680 секунд; 90 секунд отделены для review. В review отдельный запрос ограничен 45 секундами, последние 10 секунд оставляются для снимка состояния | Сложное решение может потребовать больше рассуждений; значения являются начальными настройками |
| Ограниченные повторы API | Временные ошибки повторяются в рамках общего дедлайна запроса и фазы; ошибки авторизации не повторяются | Слишком маленький request timeout может вредить медленной генерации |
| Завершение | `finish` вызывается отдельно; harness выполняет `git diff --check HEAD`, status и stat и даёт возможность исправить ошибку | Проверка diff не доказывает семантическую корректность; обычные тесты запускает агент |
| Новые файлы | `create_file` включает в diff только созданный файл через `git add -N -- path` | Игнорируемый или недоступный файл сопровождается предупреждением |
| Конкурентная оценка | Один агент последовательно меняет один репозиторий; внутри задачи нет автоматического fan-out из нескольких моделей | Это сберегает пропускную способность при 20 одновременных задачах, выигрыш измеряется отдельно |

Модель остаётся `Qwen/Qwen3.8-27B-FP8` с фиксированной ревизией, 3 независимыми
репликами и контекстом 65536. Увеличения аппаратного бюджета относительно runner
нет. Сервер должен пройти неизменённую короткую проверку bash/pwd организаторов.

## Проверки и измерение результата

Локальные проверки используют настоящие временные файлы и Git-репозитории,
реальные команды тестов и подставные ответы модели. Они проверяют код адаптера,
редактирование, протокол, таймауты и сохранение логов. Рендерится фактический
шаблон зафиксированного checkpoint Qwen. Они не проверяют качество живой модели.

Для честного сравнения подготовлен `profile=ported`: тот же fork, транспорт,
инструменты, промпт и sampling, но без checkpoint-компактации, резерва review и
обязательного finish gate. Это контроль выбранных доработок, не неизменённый
upstream default. Стандартный профиль официального сабмита — `mera`.

На GPU-сервере нужно сравнить официальную baseline-конфигурацию, ported и mera
на одном полном публичном наборе, с одной попыткой на задачу, одинаковыми
ресурсами и concurrency. Для отделения эффекта модели дополнительно использовать
одинаковую модель в сравнении harness. Считать solved/total, ошибки, таймауты,
длительность и расход токенов. Не выбирать победителя только по числу пройденных
локальных unit-тестов.

Траектории сохраняются в `mini-swe-agent.json`, запросы и checkpoints — в
`model-audit.json`, действия и финальные проверки — в `tool-audit.json`.
Это native audit logs, не обещание ATIF-совместимого экспорта.

В ветке GitHub-форка дополнительно опубликованы `scripts/`, pinned зависимости
в `mera_requirements.txt`, исходная provenance в `vendor/` и проверки в
`tests_mera/`. Для отдельного checkout форка:

```bash
uv venv --python 3.12 .venv
uv pip install --python .venv/bin/python -r mera_requirements.txt
.venv/bin/python -m unittest discover -s tests_mera -v
.venv/bin/python scripts/package_submission.py submission_stage2 --output dist/mera-mini-stage2.zip
```

Реальная сборка inference-образа, GPU startup, throughput и SWE MERA pass@1 пока
не измерены. Локальная RTX 4070 Ti SUPER 16 ГБ не вмещает эту конфигурацию модели.

## Следующие эксперименты

1. Подобрать thinking budget и timeout по фактической задержке при concurrency 20.
2. Сравнить exact editor с bash-only при одинаковых модели и бюджете времени.
3. Сравнить checkpoint с полным контекстом и подобрать порог сжатия.
4. Проверить полезность короткого независимого review внутри одной попытки,
   если оно укладывается в общий бюджет. Многократные независимые старты с
   выбором лучшего решения требуют отдельного уточнения правил.

Скрытые оценочные тесты, gold patches, подмена verifiers и готовые решения
задач не используются. Оценка и сетевые ограничения определяются организаторами.
