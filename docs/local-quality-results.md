# Локальная проверка качества: наблюдения и ограничения

Запущены **три отдельные серии живых диагностик**, по три самостоятельно
созданные Python-задачи: v001/v002 сравнивают два варианта, v003 проверяет только
новый snapshot. В каждом условии выполнена одна попытка на задачу. Это
не задачи SWE MERA, не официальный Harbor-прогон и не измерение pass@1 конкурса.
Проверки с подготовленными ответами модели в эти результаты не включены.

## Фактическая модель и среда

| Параметр | Значение |
|---|---|
| Реальный backend | Ollama native **0.17.6** |
| Реальная модель | **`qwen3:8b-q4_K_M`** |
| OpenAI-compatible alias | `qwen35-local`; имя alias не описывает фактическую модель |
| Контекст backend | 16384 токена |
| Предел вывода | 2048 токенов |
| Thinking backend | Выключен |
| Thinking budget 512 из конфигурации агента | Backend не исполняет этот контроль; это не фактические 512 thinking-токенов |
| Лимиты диагностической попытки | 240 секунд, 25 ходов, timeout запроса 120 секунд |
| Бюджет истории harness | 8000 условно оценённых токенов для обоих вариантов |
| Выполнение команд | `LocalEnvironment`/bubblewrap, task root `/testbed`, сеть инструментов отключена |
| Sampling | Запрашивается temperature 1.0; фиксированный seed не задавался |

`reasoning_effort`, `chat_template_kwargs` и `thinking_token_budget` не
поддерживаются этим локальным backend в форме vLLM; `tool_choice` работает как
автоматический выбор Ollama. Эти ограничения записаны в `backend_metadata`.
**Целевая Qwen3.8-27B-FP8 под vLLM здесь не запускалась.**

`before` — ранее упакованный mini-swe-agent fork, а не официальный baseline
Qwen3.5-9B. Его ZIP SHA256:
`40691ebf480dadd6d8594cb154371d3750948f4ff577e565defb3726497a1834`.
`after` — копия кода улучшенного агента, сделанная перед соответствующей серией.
Текущие файлы проекта могли быть доработаны позднее и не подменяют эти копии.

## Что проверялось

Все три репозитория содержали обычные доступные агенту `unittest`-тесты.
После попытки запускались также исходные версии этих тестов и независимые
проверки требований. Изменения существующих тестов, в том числе mode bits,
проверялись отдельно. Проверки скрытого набора соревнования не использовались.

| Синтетическая задача | Критерии |
|---|---|
| `options_merge` | 10: сохранить False/0/пустые значения, пропускать None, не менять входы, вернуть новый словарь |
| `intervals` | 9: перекрытия, соприкосновения, вложенные интервалы, отрицательные границы, отсутствие мутации и tuple-результат |
| `query_params` | 9: сохранить исходную query byte-for-byte, fragment, повторяющиеся ключи, list/tuple, None/пустые/Unicode и исходный mapping |

Успешная попытка требует всех критериев, исходных тестов, ненулевого patch,
сохранения HEAD и существующих тестов. Одна лишь строка «tests passed» или exit 0
произвольной команды успешной попыткой не считается.

## Серия v001: только содержательное описание

В первой серии передавался текст synthetic issue без общего публичного
wrapper SWE MERA. **Итог: before 0/3, after 0/3.** Эта серия сохраняется как
наблюдённый отрицательный результат.

| Задача | Before: критерии / время | After: критерии / время |
|---|---:|---:|
| options_merge | Модуль удалён; проверка не исполнилась / 19,6 с | Модуль удалён; проверка не исполнилась / 6,8 с |
| intervals | 7/9 / 4,5 с | 4/9 / 52,5 с |
| query_params | 3/9 / 75,6 с | 3/9 / 21,4 с |

По траекториям обнаружены конкретные проблемы:

- В обеих попытках options модель попыталась клонировать placeholder URL в
  уже заполненный `/testbed`, затем вызвала `rm -rf /testbed`. Исходники и тест
  оказались удалены, после чего модель повторяла сообщения через `echo`.
- Before/intervals исправил соприкосновение интервалов и прошёл доступные тесты,
  но не выполнил явно описанное требование сохранять границу внешнего интервала.
- After/intervals принял гипотезу автора о сортировке, затем пытался выполнить
  Python test file как shell script и менял его executable mode.
- Before/query_params многократно повторял неуспешные exact edits с literal
  `\\n` вместо нужного текста; after/query_params ушёл в pip/ensurepip/tooling loop.

Пост-аудит дополнительно обнаружил изменение mode у test file в
after/intervals, которое ранний text-only detector не отражал. Исходные данные
не переписаны: исправление отмечено отдельно в `post-audit.json`.
[Опубликованный результат и пост-аудит v001](../experiments/results/diagnostics-live-001.json).

## Серия v002: публичный формат постановки

Во второй серии оба варианта получили одинаковый общий wrapper из публичной
постановки: `<uploaded_files>`, `<issue_description>`, готовые зависимости,
non-test/repository constraints и все восемь фаз. Исходное issue публичной
задачи из шаблона удалено и заменено synthetic issue. Это **другое условие
эксперимента**, поэтому 0/3 → 1/3 нельзя приписывать изменению harness.

В after snapshot этой серии также присутствовали новые startup/review и
repository-preservation меры. Итог внутри v002: **before 1/3, after 1/3**.

| Задача | Before: критерии / время | After: критерии / время |
|---|---:|---:|
| options_merge | **10/10**, решена / 20,0 с | **10/10**, решена / 16,2 с |
| intervals | 6/9, не решена / 222,7 с | 7/9, не решена / 10,7 с |
| query_params | 3/9, не решена / 124,8 с | 5/9, не решена / 21,4 с |

В after/intervals прошли обычные тесты, но остались два невыполненных критерия
вложенности. В after/query_params обычные тесты также прошли, а независимая
проверка всё ещё обнаружила потерю части требований. Быстрое завершение этих
попыток не считается доказательством ускорения успешного решения.

Новый review/file-constraint механизм дал наблюдаемую техническую пользу:
в options и query модель сначала выполнила `chmod +x` существующего теста,
получила замечание перед finish и восстановила mode 644. После серии v002
пост-аудит не обнаружил изменений существующих тестов.

Осталось важное ограничение: `python3 test_solution.py` возвращает 0 даже если
файл лишь определяет unittest-классы и не запускает их. Модель использовала
такую команду и ошибочно считала её подтверждением тестов. Диагностический
грейдер использовал настоящий `python3 -m unittest`, поэтому итоговые результаты
этой ошибкой не улучшены. Harness должен различать exit code команды и факт
обнаружения/выполнения тестов, сохраняя возможность тихих assert-reproducers.
[Опубликованный результат и пост-аудит v002](../experiments/results/diagnostics-live-002.json).

## Серия v003: after-only, дополнительный reviewer

Третья серия использовала те же три synthetic issue, общий публичный wrapper,
8B Q4 backend с выключенным thinking и прежние лимиты. Проверен только новый
snapshot: literal `search`, восстановление после повторяющихся неуспешных
действий и включённый дополнительный model reviewer (`semantic_review=True`).
Итог — **1/3 решена**; контрольного before-прогона в этой серии нет.

| Задача | Критерии | Время |
|---|---:|---:|
| options_merge | **10/10**, решена | 70,228 с |
| intervals | 7/9, не решена | 18,891 с |
| query_params | 2/9, не решена | 129,598 с |

Reviewer выдал неверный совет уже на правильную проверку `value is not None`:
утверждал, что она не сохраняет False/0/пустые значения. Агент изменил верный
patch, затем восстановил его после настоящего запуска тестов. В intervals
reviewer ошибочно одобрил сохранение внешней границы вложенного интервала,
хотя `result[-1][1] = end` по-прежнему уменьшает её. Два независимых критерия
вложенности снова не прошли. В query_params финальная попытка не выполнила
семь из девяти требований.

Эта серия не подтверждает прироста качества от reviewer или нового search.
Из-за наблюдённого неверного совета production-конфигурация оставляет
**`semantic_review=False` по умолчанию**. Полный diff и журнал реальных команд
проверяются при завершении независимо от дополнительного model reviewer.
Настройка production отличается от проверенного v003 snapshot; его результат
нельзя выдавать за результат текущего production-профиля.
[Опубликованный результат v003](../experiments/results/diagnostics-live-003.json).

## Публичная задача Click: две отдельные попытки

Отдельно проверена постановка **py-009** на публичном Click checkout `d73083e`.
Использованы та же фактическая `qwen3:8b-q4_K_M` и среда, с лимитом 360 секунд
и 40 ходов. Это локальная проверка по описанному публичному поведению и обычным
тестам проекта; официальный verifier и скрытые тесты не запускались.

**Попытка не решила задачу:** 81,86 секунды, все 40 ходов, остановка
`LimitsExceeded`, исходники не изменены, обязательный непустой `change.diff`
отсутствует. Независимые проверки публичных требований остались на 4/6; обычные
11 help-тестов проходили уже до исправления и продолжили проходить. Их успех
не подтверждает устранение конкретной ошибки из issue.

В траектории модель искала `-h`/`--help` shell-командами без разделителя `--`,
получала справку search utility, затем повторяла exact edits с отсутствующим
текстом в example-файле вместо перехода к реализации библиотеки. Это основание
для literal `search` tool и подсказки перечитать точный target после неуспешного
edit. Новый tool добавлен после этой попытки.
[Опубликованный результат Click001](../experiments/results/public-click-live-001.json).

Во второй попытке Click002 использован новый snapshot с `semantic_review=False`,
включённым thinking и пределом вывода **8192** вместо 2048 токенов. Фактическая
модель осталась `qwen3:8b-q4_K_M`/Ollama 0.17.6, alias изменён на
`qwen3-8b-local`; контекст backend — 16384. Одновременно изменились harness и
настройки inference, поэтому различия нельзя приписывать одному из них. Это
следующий диагностический эксперимент после уже изученного провала, а не новая
независимая оценка pass@1.

**Click002 также не решила задачу:** 350,244 секунды, 26 ходов, остановка
`time_budget`. Агент изменил `src/click/core.py`, но обе целевые ошибки из issue
сохранились; публичные проверки остались на **4/6 до и после**. Появился также
дубликат `--help, --help` в help output. Обычные 11 help-тестов проекта снова
прошли до и после попытки. Собственный вызов агента с отсутствующим
`tests/test_click_core.py` завершился exit 4 и нулём тестов; журнал проверок
явно показал эту неудачу перед finish.

Экспорт обязательного артефакта сработал: `change.diff` непустой, содержит одну
замену в `src/click/core.py`, применим к исходному checkout (`git apply --check`
и применение вернули 0), существующие тесты и HEAD сохранены. После применения
именно доставленного patch к чистой копии результат вновь **4/6**, обычные тесты
**11 passed**. То есть исправлена доставка patch, но правильного решения нет.
SHA256 артефакта:
`a0160a912006da54baf1690ce63c3420339ad2c73cf67d7f78ad22795cd2751d`.
[Опубликованный результат Click002](../experiments/results/public-click-live-002.json).

В опубликованных JSON есть mapping исходников, metadata модели, параметры,
реальные результаты доступных и независимых проверок, а также SHA256 исходных
локальных отчётов. Для v001/v002 включён отдельный пост-аудит. Сырые каталоги
попыток с statement, patch и model/tool audit остаются локальными и не входят
в публикуемые отчёты. Пост-аудит Git выполнен внутри той же изоляции;
модель-изменяемый Git config не запускается на host.

На трёх задачах и одной стохастической попытке нет доказательства глобального
прироста качества. В частности, число полностью решённых задач v002 одинаково.
Получены конкретные failure modes и проверка технических механизмов, а не
оценка выбранной production-модели. Для подтверждения качества нужен одинаковый
полный публичный набор, один и тот же backend и заявленные аппаратные лимиты.
