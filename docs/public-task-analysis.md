# Анализ публичных постановок SWE MERA

Проверены все **49 публичных `instruction.md` и `task.toml`** из commit
`070bcb675d96845745e28b40f3830c98139217ea`: 18 Go, 15 PHP, 16 Python.
Файлы решений, gold patches, исходники evaluation tests и verifier не читались.
Из `task.toml` использовались только метаданные задачи и ограничения окружения.
Это описание публичного набора, не анализ скрытых 53 задач Stage II.
[Каталог источников](https://github.com/MERA-Evaluation/SWE-MERA-CHALLENGE/tree/070bcb675d96845745e28b40f3830c98139217ea/tasks).

Оригинальные постановки сохранены в `data/public_statements/`, инвентарь с
неизменяемыми URL, Git blob SHA и SHA256 файлов — в
`data/public_task_inventory.json`. Эти данные не должны попадать в ZIP агента.

Последние четыре счётчика получены простыми текстовыми маркерами, указанными в
JSON-инвентаре, а не ручной разметкой всех семантических типов задач. Код может
быть и без fenced block; отсутствие маркера не доказывает отсутствие reproducer.
Длина содержательной части issue: минимум 62, медиана 1477, максимум 4676 символов.

Особенно важен конфликт boilerplate: общая фаза предлагает устанавливать
окружение и создавать тесты, а конкретный контракт сообщает о готовых
зависимостях и minimal non-test patch. Harness должен явно удерживать этот
контракт. Отдельный небольшой reproducer внутри репозитория допустим по тексту
постановки; перед сдачей нужно убрать только собственные временные артефакты,
сохранив исходные файлы и уже существующие изменения.
[Пример полной постановки Go](https://github.com/MERA-Evaluation/SWE-MERA-CHALLENGE/blob/070bcb675d96845745e28b40f3830c98139217ea/tasks/go-001/instruction.md),
[пример Python](https://github.com/MERA-Evaluation/SWE-MERA-CHALLENGE/blob/070bcb675d96845745e28b40f3830c98139217ea/tasks/py-009/instruction.md).

## Обязательный `change.diff` — часть результата

В **22 из 49** постановок есть отдельная секция `Submission`: собрать полный
unified diff в `/testbed/change.diff`; по её тексту собирается именно этот файл.
В той же секции указаны применимость к исходному checkout через `git apply`,
запрет добавлять или менять test files, бинарные blobs и generated artifacts.
Этот контракт находится в доступной агенту постановке. Для его обнаружения не
нужны gold patches, скрытые тесты или чтение verifier.
[Пример PHP](https://github.com/MERA-Evaluation/SWE-MERA-CHALLENGE/blob/070bcb675d96845745e28b40f3830c98139217ea/tasks/php-003/instruction.md),
[пример Python](https://github.com/MERA-Evaluation/SWE-MERA-CHALLENGE/blob/070bcb675d96845745e28b40f3830c98139217ea/tasks/py-009/instruction.md).

Следствие для качества: семантически правильные исходники могут не дать
результат, если обязательный файл отсутствует, diff не применяется либо в него
попали reproduction/tests/binaries. Само наличие `change.diff` тоже не доказывает
корректность исправления. Проверка применимости и обычные тесты отвечают на
разные вопросы.

Текущий `task_contract.py` распознаёт требуемый путь из секции вывода самой
постановки, а не по ID задачи. Перед завершением он строит diff относительно
исходного HEAD во временном Git index, исключает собственный выходной файл и
проверяет file constraints и `git apply --cached --check` на отдельном исходном
index. Настоящий index и рабочие изменения сохраняются. Экспорт вызывается также
при штатном выходе по внутренним лимитам; его неуспех записывается явно.
Для остальных постановок отдельный файл не создаётся автоматически.

Проверки parser/exporter подтверждают обработку контракта и применимость diff,
но не прохождение целевой модели или скрытых оценочных тестов.

## Какие изменения дадут проверяемую пользу

1. **Короткий контракт перед первым действием.** Извлечь из полной постановки
   содержимое `<issue_description>` и отдельно напомнить ограничения. Сохранить
   сам оригинал и все примеры. Агент должен сформулировать наблюдаемое поведение,
   ожидаемое поведение, совместимость и критерий проверки. Не превращать это в
   ещё один большой LLM-вызов или task-specific таблицу решений.

2. **Контекст репозитория до выбора команды тестов.** Узнать фактический проект
   по README, manifests и расположению исходников. Для Python читать настройки
   pytest/tox/pyproject; для Go — go.mod и package layout; для PHP — composer
   scripts, phpunit/pest config и уже установленный vendor. Сначала узкий тест,
   затем соседний пакет, полный suite — только при достаточном времени.
   Синтаксическая проверка не должна считаться подтверждением семантики.

3. **Воспроизведение до и после одного и того же изменения.** Сохранить команду
   и фактический результат. Проверять пример из issue и ближайшие граничные
   случаи, выводя их из изменённой ветки и существующих API. Если воспроизведение
   требует внешнего сервиса или секрета, использовать принятые в проекте mocks
   или более узкую проверку, а не живой внешний аккаунт.

4. **Проверка всего требования, а не первого исключения.** API feature может
   требовать wiring в CLI, конфигурации и сериализации; numerical bug — формы
   результата и совместимости, а не только исчезновения crash. Перед finish
   сверять каждый заявленный критерий с diff и наблюдаемыми проверками. Не
   фиксировать количество критериев или точный файл по ID публичной задачи.

5. **Проверяемая память.** В checkpoint хранить исходную цель, ограничения,
   подтверждённые факты, гипотезы, изменения и команды с их результатами.
   Разделять ожидаемое поведение из issue и объяснение автора: объяснение может
   быть неполным или ошибочным. Не записывать гипотезу как установленную причину.

6. **Финальный patch без побочных изменений.** Запомнить исходный git status,
   следить за созданными reproducer/temporary файлами и изменениями тестов,
   просмотреть полный diff и статус. Удалять только свои временные файлы;
   не выполнять безусловный reset/checkout тестовых директорий. Сохранять
   незавершённый полезный patch при истечении времени, честно указав проверки.

## Почему нельзя ориентироваться только на язык из metadata

Некоторые Go-проекты исполняют JavaScript или собственный DSL; пример на другом
языке описывает поведение интерпретатора, а исправление находится в Go.
В PHP-каталоге встречаются frontend и workflow задачи. Поэтому language hint
должен помогать найти tooling, а не заставлять менять только файлы данного языка.
[Go с JS reproducer](https://github.com/MERA-Evaluation/SWE-MERA-CHALLENGE/blob/070bcb675d96845745e28b40f3830c98139217ea/tasks/go-009/instruction.md),
[PHP с frontend проблемой](https://github.com/MERA-Evaluation/SWE-MERA-CHALLENGE/blob/070bcb675d96845745e28b40f3830c98139217ea/tasks/php-007/instruction.md),
[workflow задача](https://github.com/MERA-Evaluation/SWE-MERA-CHALLENGE/blob/070bcb675d96845745e28b40f3830c98139217ea/tasks/php-005/instruction.md).

Две очень короткие постановки — 62 и 164 символа содержательной части — требуют
изучения аналогичных публичных API и существующих соглашений в checkout.
Для них длинная процедура пересказа задачи не заменяет чтения кода.
[Короткая API-задача](https://github.com/MERA-Evaluation/SWE-MERA-CHALLENGE/blob/070bcb675d96845745e28b40f3830c98139217ea/tasks/py-016/instruction.md),
[короткая CLI-задача](https://github.com/MERA-Evaluation/SWE-MERA-CHALLENGE/blob/070bcb675d96845745e28b40f3830c98139217ea/tasks/py-006/instruction.md).

## Локальная проверка

Самый очевидный небольшой pure-Python кандидат из прочитанных постановок —
`py-009`, Click: issue содержит воспроизводимый CLI пример, ожидаемое сообщение,
версию Python и Click, а также short commit `d73083e`. В Python `task.toml`
этого набора нет полей repo/base_commit, поэтому exact base нельзя выдумывать:
проверить commit или использовать официальный task image. Другие Python задачи
могут потребовать scientific/C dependencies, frontend, внешние сервисы либо
не содержать имени репозитория из-за redaction.

Все 49 публичных task.toml задают agent timeout 3600 секунд, 2 CPU, 4096 МБ RAM
и 0 GPU именно task-контейнеру. Это отличается от рекламируемого приватного
лимита до 30 минут. Inference GPU — отдельный ресурс. Не увеличивать автоматически
бюджет официального сабмита до часа на основании публичной metadata и не
смешивать local public result с private score.
[Публичная metadata](https://github.com/MERA-Evaluation/SWE-MERA-CHALLENGE/blob/070bcb675d96845745e28b40f3830c98139217ea/tasks/py-009/task.toml).

Локальный запуск с живой моделью должен отдельно сообщать модель, precision,
context/token/time limits, исходный commit, тип окружения и результат. Результат
на маленькой модели или вручную подготовленном checkout не является проверкой
целевой Qwen3.8-27B-FP8 или официальным Harbor pass@1. Unit-тесты с scripted
ответами проверяют адаптер, но не качество выбора правок моделью.
